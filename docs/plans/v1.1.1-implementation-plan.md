# Split View Router v1.1.1 Implementation Plan

## Release objective

Ship a low-risk maintenance release that improves resilience and diagnosability around rare Firefox extension storage failures without changing the public workflow, storage schema, routing behavior, pair/session restore behavior, or user-facing feature set.

This release should treat the recently observed failure as a defensive-hardening issue, not as a critical architectural rewrite.

## Background

Observed failure mode:

- The toolbar popup displayed `Extension is reloading…`.
- Popup controls did not work.
- Tab context-menu actions did not work.
- The diagnostics/options page also failed.
- Firefox extension console showed:

```text
Error: An unexpected error occurred background.js:43:27
    logQueue moz-extension://.../background.js:43
    log moz-extension://.../background.js:35
    <anonymous> moz-extension://.../background.js:499
```

The relevant path is diagnostic logging:

```js
const stored = await browser.storage.local.get([LOG_KEY, LOGGING_KEY]);
...
await browser.storage.local.set({[LOG_KEY]: buf});
```

The extension stores very small state, and the diagnostic log is already capped at 50 entries. There is no evidence that the extension is writing large enough data to normally exhaust storage. The more likely cause is a rare Firefox extension storage/install-state failure that the add-on did not handle defensively.

The fix for v1.1.1 is to make that rare state easier to diagnose and recover from, while preventing nonessential diagnostics logging from worsening the failure.

## Release scope

### In scope

- Make diagnostic logging non-fatal.
- Add an in-memory diagnostics log fallback.
- Replace misleading popup text with a more accurate state-unavailable message.
- Add storage/background health checks to the diagnostics/options page.
- Add a manual `Reset extension data` button to the diagnostics/options page.
- Add a simple background `ping` handler that does not touch storage.
- Preserve all existing storage keys and formats.
- Preserve existing routing and pairing behavior.
- Preserve existing session-restore behavior.

### Out of scope for v1.1.1

- Do not change `persistent: false` to `persistent: true`.
- Do not introduce a new runtime state architecture.
- Do not make `storage.session` a fallback state store yet.
- Do not auto-reset all extension data.
- Do not change pair/session marker semantics.
- Do not change default mode or routing defaults.
- Do not migrate or rename storage keys.

## Compatibility constraints

Existing users must keep their current state and workflow.

Keep these storage keys unchanged:

```js
const PAIRS_KEY = "pairs";
const MODE_KEY = "mode";
const ROUTING_KEY = "routing";
const PAUSED_KEY = "paused";

```

Keep these defaults unchanged:

```js

```

Keep pair storage shape unchanged:

```js
{
  [leftTabId]: rightTabId
}
```

Keep tab session marker shape unchanged:

```js
{
  pairId,
  side: "left" | "right",
  paused: boolean
}
```

## Implementation plan

## 1. Make diagnostic logging non-fatal

### Problem

`log()` currently reads/writes `browser.storage.local`. If storage is unavailable, logging fails. Logging is diagnostic-only and should never block popup, routing, pairing, context menus, or diagnostics rendering.

### Required behavior

- Logging must never throw outward.
- Logging must always append to an in-memory ring buffer first.
- If `storage.local` works, mirror the log to storage as before.
- If `storage.local` fails, preserve recent events in memory and record storage health.
- Avoid infinite recursion: storage errors inside `log()` must not call `log()` again.

### Suggested implementation

Add near the log constants:

```js
const memoryLog = [];
const health = {
  storageLocal: {
    ok: true,
    lastError: null,
    lastCheckedAt: null
  }
};

function rememberStorageFailure(e) {
  health.storageLocal.ok = false;
  health.storageLocal.lastError = String(e?.message || e);
  health.storageLocal.lastCheckedAt = new Date().toISOString();
}

function rememberStorageSuccess() {
  health.storageLocal.ok = true;
  health.storageLocal.lastError = null;
  health.storageLocal.lastCheckedAt = new Date().toISOString();
}

function pushMemoryLog(entry) {
  memoryLog.push(entry);
  while (memoryLog.length > LOG_MAX) memoryLog.shift();
}
```

Replace `log()` with a non-fatal implementation:

```js
let logQueue = Promise.resolve();

function log(src, lvl, msg, data) {
  const entry = {t: Date.now(), src, lvl, msg, data: data || null};
  pushMemoryLog(entry);

  logQueue = logQueue.then(async () => {
    try {
      const stored = await browser.storage.local.get([LOG_KEY, LOGGING_KEY]);
      rememberStorageSuccess();

      if (stored[LOGGING_KEY] === false) return;

      const buf = Array.isArray(stored[LOG_KEY]) ? stored[LOG_KEY] : [];
      buf.push(entry);
      while (buf.length > LOG_MAX) buf.shift();

      await browser.storage.local.set({[LOG_KEY]: buf});
      rememberStorageSuccess();
    } catch (e) {
      rememberStorageFailure(e);
      console.warn("[SVR] diagnostic logging storage failed; using memory log only", e);
    }
  }).catch((e) => {
    console.warn("[SVR] diagnostic logging queue failed", e);
  });

  return logQueue;
}
```

### Acceptance criteria

- Storage failure inside `log()` does not produce unhandled promise rejection.
- Extension routing still works when log storage write fails.
- Recent log entries remain available from memory through diagnostics.
- Existing `logging` preference is respected when storage is readable.
- If `logging` preference cannot be read, logging to memory continues.

## 2. Add safe storage helpers for diagnostics and reset paths

### Problem

The extension directly calls `browser.storage.local.get()` in several places. For v1.1.1, avoid a broad refactor, but add small helper functions where diagnostics/reset need reliable error reporting.

### Required behavior

- Health checks should capture exact storage read/write/remove failures.
- Reset should report success/failure clearly.
- Do not silently wipe data except when the user explicitly clicks reset.

### Suggested implementation

Add helpers:

```js
async function testStorageLocal() {
  const result = {
    read: {ok: false, error: null},
    write: {ok: false, error: null},
    remove: {ok: false, error: null}
  };

  const key = "__svr_healthcheck__";

  try {
    await browser.storage.local.get(LOGGING_KEY);
    result.read.ok = true;
  } catch (e) {
    result.read.error = String(e?.message || e);
  }

  try {
    await browser.storage.local.set({[key]: Date.now()});
    result.write.ok = true;
  } catch (e) {
    result.write.error = String(e?.message || e);
  }

  try {
    await browser.storage.local.remove(key);
    result.remove.ok = true;
  } catch (e) {
    result.remove.error = String(e?.message || e);
  }

  result.ok = result.read.ok && result.write.ok && result.remove.ok;
  return result;
}
```

### Acceptance criteria

- Diagnostics can distinguish read, write, and remove failures.
- Health check does not change user state.
- Temporary health-check key is removed when possible.

## 3. Add background ping and health messages

### Problem

The diagnostics page currently depends on `getDiagnostics`, which itself reads storage. If that fails, diagnostics cannot tell whether the background is alive, storage is broken, or both.

### Required behavior

Add message handlers that are safe and minimally dependent:

```js
if (msg.type === "ping") {
  return {
    ok: true,
    generatedAt: new Date().toISOString(),
    extension: browser.runtime.getManifest(),
    browser: {
      userAgent: navigator.userAgent,
      platform: navigator.platform
    }
  };
}

if (msg.type === "getHealth") {
  return {
    generatedAt: new Date().toISOString(),
    background: {ok: true},
    storageLocal: await testStorageLocal(),
    memory: {
      logEntries: memoryLog.length,
      storageLastError: health.storageLocal.lastError
    }
  };
}
```

Do not call `getPairs()`, `getRouting()`, or `getPausedPairs()` from `ping`.

### Acceptance criteria

- `ping` works even when `storage.local` fails.
- `getHealth` returns storage health if the background is running.
- `getHealth` does not require existing extension state to be valid.

## 4. Improve popup failure message

### Problem

The popup currently displays:

```text
Extension is reloading…
```

when `getPairs` fails. That message is misleading for storage failures or background failures.

### Required behavior

Only show failure text in the pair-list area when pair retrieval fails. Do not add a permanent health/status line to the popup during normal operation.

Suggested message:

```text
Extension state unavailable.
Open Add-on Preferences → Diagnostics, or reload the extension.
```

Optional compact variant for popup width:

```text
Extension state unavailable. Open Diagnostics or reload.
```

Suggested code change in `popup.js`:

```js
} catch (e) {
  const err = document.createElement('div');
  err.className = 'small error';
  err.textContent = 'Extension state unavailable. Open Diagnostics or reload.';
  list.appendChild(err);
  console.error("[SVR] getPairs failed:", e);
  return;
}
```

Do not show stack traces in the popup.

### Acceptance criteria

- Normal popup remains unchanged.
- Error only replaces pair-list content when `getPairs` fails.
- Message does not claim the extension is reloading unless reload is actually known.
- Popup logs the actual error to console for developer inspection.

## 5. Add diagnostics-page health section

### Problem

The diagnostics page currently calls `getDiagnostics` and, if that fails, only displays a generic error. It should provide partial diagnosis even when storage-backed diagnostics fail.

### Required behavior

Render a static diagnostics shell immediately before any background calls complete.

Recommended layout:

```text
Diagnostics

Health
- Background: Checking...
- Local storage read: Checking...
- Local storage write: Checking...
- Local storage remove: Checking...

Current State
...

Recent Events
...

Recovery
[Reset extension data]
[Reload diagnostics]
[Copy diagnostics]
```

The page should:

1. Render the Recovery section immediately.
2. Call `ping`.
3. Call `getHealth`.
4. Call `getDiagnostics`.
5. If `getDiagnostics` fails, still show `ping` and `getHealth` results.
6. Produce copyable diagnostics text containing all available results.

### Suggested options.js flow

```js
async function refresh() {
  renderStaticShell();

  const report = {
    generatedAt: new Date().toISOString(),
    page: {
      url: location.href,
      userAgent: navigator.userAgent,
      manifest: browser.runtime.getManifest()
    },
    ping: null,
    health: null,
    diagnostics: null,
    errors: []
  };

  try {
    report.ping = await browser.runtime.sendMessage({type: "ping"});
  } catch (e) {
    report.errors.push({step: "ping", error: String(e?.message || e)});
  }

  try {
    report.health = await browser.runtime.sendMessage({type: "getHealth"});
  } catch (e) {
    report.errors.push({step: "getHealth", error: String(e?.message || e)});
  }

  try {
    report.diagnostics = await browser.runtime.sendMessage({type: "getDiagnostics"});
  } catch (e) {
    report.errors.push({step: "getDiagnostics", error: String(e?.message || e)});
  }

  renderReport(report);
}
```

### Acceptance criteria

- Diagnostics page shows extension version and user agent even if background calls fail.
- Diagnostics page differentiates:
  - background not responding
  - storage read failure
  - storage write failure
  - diagnostics retrieval failure
- Copy diagnostics works with partial data.
- Existing current-state and log rendering still work when `getDiagnostics` succeeds.

## 6. Add manual reset button on diagnostics page

### Problem

A rare storage failure may require user-initiated recovery. Reinstall should not be the first recovery path.

### Required behavior

Add a `Reset extension data` button in a Recovery section on the diagnostics/options page.

Do not put this button in the popup.

Do not auto-reset full data.

### User-facing text

Before reset, show confirmation text:

```text
Reset extension data?
This clears saved pairs, routing mode, pause state, and diagnostic logs.
Open tabs are not closed.
```

After success:

```text
Reset complete. Reload the extension or restart Firefox if the issue continues.
```

After failure:

```text
Reset failed: <error>
Firefox extension storage may be unavailable. Remove and reinstall the extension if the issue continues.
```

### Reset implementation

Add background handler:

```js
if (msg.type === "resetExtensionData") {
  const result = {
    storageLocal: {ok: false, error: null},
    storageSession: {ok: null, error: null},
    sessionMarkers: {ok: false, cleared: 0, failed: 0, error: null},
    defaults: {ok: false, error: null},
    menus: {ok: false, error: null}
  };

  try {
    await browser.storage.local.clear();
    result.storageLocal.ok = true;
  } catch (e) {
    result.storageLocal.error = String(e?.message || e);
  }

  try {
    if (browser.storage.session?.clear) {
      await browser.storage.session.clear();
      result.storageSession.ok = true;
    }
  } catch (e) {
    result.storageSession.ok = false;
    result.storageSession.error = String(e?.message || e);
  }

  try {
    const tabs = await browser.tabs.query({});
    const results = await Promise.allSettled(
      tabs.map(tab => browser.sessions.removeTabValue(tab.id, MARKER_KEY))
    );
    result.sessionMarkers.cleared = results.filter(r => r.status === "fulfilled").length;
    result.sessionMarkers.failed = results.filter(r => r.status === "rejected").length;
    result.sessionMarkers.ok = result.sessionMarkers.failed === 0;
  } catch (e) {
    result.sessionMarkers.error = String(e?.message || e);
  }

  try {
    await browser.storage.local.set({
      [MODE_KEY]: "simple",
      [ROUTING_KEY]: true,
      [PAIRS_KEY]: {},
      [PAUSED_KEY]: [],
      [LOG_KEY]: []
    });
    memoryLog.length = 0;
    result.defaults.ok = true;
  } catch (e) {
    result.defaults.error = String(e?.message || e);
  }

  try {
    await createContextMenus();
    await updateBadge();
    result.menus.ok = true;
  } catch (e) {
    result.menus.error = String(e?.message || e);
  }

  return result;
}
```

Notes:

- Use `Promise.allSettled` for marker clearing so one bad tab does not abort all cleanup.
- If `storage.local.clear()` fails, still attempt session marker cleanup and menu recreation.
- If defaults cannot be written, report failure clearly.

### Acceptance criteria

- Reset button is visible even if `getDiagnostics` fails.
- Reset requires explicit user confirmation.
- Reset does not close tabs.
- Reset clears local storage when possible.
- Reset clears tab session markers when possible.
- Reset recreates context menus when possible.
- Reset result is shown in the page and included in copied diagnostics.

## Rollout guidance

- Release as `v1.1.1`.
- Treat as maintenance/hardening.
- Do not mention a critical data-corruption fix unless verified.
- AMO release note should be concise:

```text
Improves diagnostics and recovery for rare Firefox extension-storage failures. Adds a manual reset action in preferences and makes diagnostic logging non-blocking. No routing or pairing workflow changes.
```

## Regression risks

| Area | Risk | Mitigation |
|---|---:|---|
| Logging | Low | Keep stored log format unchanged |
| Popup | Low | Only change failure text |
| Diagnostics page | Low/medium | Render existing diagnostics when available; add partial report only as fallback |
| Reset button | Medium | Require confirmation; place only on diagnostics page |
| Session markers | Medium | Only clear during manual reset |
| Context menus | Low | Recreate after reset; do not alter normal creation flow |

## Definition of done

- Existing extension workflow remains unchanged for healthy users.
- The popup no longer says `Extension is reloading…` for generic state failures.
- Diagnostic logging cannot break extension behavior.
- Diagnostics page can show partial health information when full diagnostics fail.
- Manual reset is available from diagnostics page and reports structured results.
- No automatic destructive reset is introduced.
- Tests pass: `npm test`, `npm run lint`, and existing e2e smoke tests if available.
